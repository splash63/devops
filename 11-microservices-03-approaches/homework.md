### Выбор: GitLab (SaaS) + GitLab Runner на собственных серверах

**Почему GitLab:**

- **Один продукт вместо набора.** Git-репозитории, CI/CD, Container Registry, окружения (environments) и права доступа живут в одном месте. Не нужно интегрировать CI-сервер с отдельным Git-хостингом.
- **Репозиторий на сервис.** Каждый микросервис лежит в своём проекте, группы проектов позволяют выдавать права по командам.
- **Шаблоны.** Общие шаги сборки выносятся в отдельный репозиторий `ci-templates` и подключаются через `include`. Сервис переопределяет только свои параметры.
- **Runner'ы на своих серверах.** GitLab Runner с Docker- или Kubernetes-executor запускается на собственных машинах. Сборки на них не расходуют облачные минуты, а число параллельных задач ограничено только ресурсами и параметром `concurrent`.
- **Собственные образы.** Образы сборки хранятся в Container Registry и подключаются ключом `image:`.
- **Секреты.** Masked и protected переменные, файловые переменные, а для повышенных требований интеграция с HashiCorp Vault. Protected-переменные доступны только защищённым веткам и тегам.
- **Параллельные тесты.** Ключ `parallel` разбивает тесты на N job'ов.

**Как это работает вместе:**

1. Разработчик делает push или открывает merge request, GitLab сам создаёт pipeline (события из VCS).
2. Pipeline забирает свободный runner, и job запускается в контейнере из нужного образа.
3. Стадии: `build` → `test` (параллельно) → `image` (сборка образа через Kaniko или BuildKit и публикация в Registry) → `deploy`.
4. Деплой в тестовое окружение идёт автоматически, в production после ручного подтверждения (`when: manual` или protected environment). Развёртывание выполняется через Helm/kubectl или Ansible.
5. Ручной запуск выполняется кнопкой Run pipeline с указанием переменных.

Пример подключения шаблона в репозитории сервиса:

```yaml
include:
  - project: 'platform/ci-templates'
    ref: v1.0.0
    file: '/templates/docker-service.yml'

variables:
  SERVICE_NAME: orders

unit-tests:
  extends: .test-template
  parallel: 4
```

**Альтернатива:** GitHub Actions закрывает те же требования и был бы равноценным выбором, если компания уже на GitHub. TeamCity сильна в настройке сборок, но не хранит код, и появляется вторая система для интеграции.

### Выбор: Elastic Stack (Filebeat → Logstash → Elasticsearch → Kibana)

**Соответствие требованиям:**

- **Сбор со всех хостов и минимальные требования к приложениям.** Приложение просто пишет в stdout. Docker сохраняет вывод в JSON-файлы, Filebeat читает их и обогащает записи метаданными (контейнер, образ, хост, метки Kubernetes). Менять код сервисов не нужно.
- **Гарантированная доставка.** Filebeat запоминает позицию чтения в registry и повторяет отправку, пока не получит подтверждение. Logstash с персистентной очередью (`queue.type: persisted`) не теряет данные при перезапуске. Доставка at-least-once, поэтому дубликаты предотвращаются детерминированным `_id` документа (fingerprint).
- **Поиск и фильтрация.** Elasticsearch индексирует поля, поэтому доступны полнотекстовый поиск и фильтры по сервису, уровню, trace-id, времени.
- **Интерфейс для разработчиков.** В Kibana разработчикам выдаются роли, а Spaces и индекс-паттерны ограничивают видимость логами своих сервисов.
- **Ссылки на сохранённый поиск.** Discover сохраняет запросы (saved search) и создаёт короткие ссылки, которыми делятся в тикетах и чатах.

**Схема взаимодействия:**

Сервис (stdout) → лог-файл Docker → **Filebeat** (на каждом хосте) → **Logstash** (парсинг, обогащение, очередь на диске) → **Elasticsearch** (кластер, реплики шардов, ILM: hot → warm → удаление) → **Kibana**.

Для больших нагрузок между Filebeat и Logstash можно поставить Kafka как буфер. Хранение регулируется политиками жизненного цикла индексов.

**Альтернатива:** Loki дешевле по ресурсам, но слабее в поиске по содержимому. Он имеет смысл, если важнее экономия и единый интерфейс Grafana.

### Выбор: Prometheus + Grafana (exporter'ы, Alertmanager)

**Соответствие требованиям:**

- **Метрики со всех хостов и их ресурсов.** На каждом хосте работает node_exporter, который отдаёт CPU, RAM, диски и сеть.
- **Ресурсы каждого сервиса.** cAdvisor на каждом хосте показывает потребление CPU, памяти, диска и сети по каждому контейнеру. В Kubernetes добавляется kube-state-metrics.
- **Метрики самих сервисов.** Сервисы подключают клиентскую библиотеку Prometheus (Java, Go, Python, Node.js и др.) и отдают бизнес-метрики (запросы, ошибки, задержки, размер очереди) на `/metrics`. Для короткоживущих задач используется Pushgateway.
- **Запросы и агрегация.** PromQL позволяет агрегировать данные по сервису, хосту, версии: `sum by (service) (rate(http_requests_total[5m]))`.
- **Панели.** Grafana подключается к Prometheus и позволяет каждой команде собирать собственные дашборды, а также хранить их как код (provisioning, JSON в Git).

**Схема взаимодействия:**

Prometheus сам опрашивает (pull) цели: node_exporter, cAdvisor, `/metrics` сервисов. Список целей определяется автоматически через service discovery, поэтому новые контейнеры подхватываются без правки конфигурации. Данные сохраняются в локальную TSDB. **Alertmanager** получает правила алертов и рассылает уведомления (почта, Telegram, Slack). **Grafana** читает данные и показывает дашборды.

Для долгого хранения и масштабирования можно добавить Thanos, Mimir или VictoriaMetrics как remote storage. Prometheus рекомендуется запускать парой одинаковых экземпляров для надёжности.

**Почему не остальные:** Zabbix хорош для классического мониторинга хостов, но контейнеры и метрики приложений в нём настраиваются тяжелее. Datadog удобен, но платный и выносит данные за периметр компании.

## Итоговая схема

Разработчик → **GitLab** (код, CI/CD, Registry) → runner'ы на своих серверах → деплой в окружения. Сервисы пишут логи в stdout → **Filebeat → Logstash → Elasticsearch → Kibana**. Метрики хостов, контейнеров и сервисов собирает **Prometheus**, визуализирует **Grafana**, оповещает **Alertmanager**. Конфигурация всех компонентов хранится в Git и применяется через CI/CD (Terraform, Ansible, Helm).
