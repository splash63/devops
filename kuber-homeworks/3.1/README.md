## 2. Рабочие ноды и запас на отказ

Выбираю рабочую ноду с **8 vCPU и 16 GiB RAM**. Закладываю на каждой **1 vCPU и 2 GiB** для ОС, kubelet, контейнерного рантайма и фоновых компонентов (например, сетевого агента). Бюджет для приложения — **7 vCPU и 14 GiB** на ноду. Это оценка: при настройке кластера нужно сверить фактический Allocatable и requests системных Pod, не учитывая их дважды.

Две ноды дают 14 vCPU и 28 GiB — этого недостаточно. Три дают 21 vCPU и 42 GiB. Чтобы эти три оставались доступны после отказа, нужен ещё один worker: **всего 4 worker-ноды**.

Три выделенные управляющие ноды с реплицируемым хранилищем состояния (например, etcd при соответствующей конфигурации Kubernetes) сохраняют кворум при потере одной. Параметры — начальная оценка для небольшого кластера. Для управляющих нод нужны SSD с низкой задержкой. Размер дисков для БД, кеша (если нужна персистентность), журналов и резервных копий нельзя вывести из объёма ОЗУ: его нужно оценить отдельно по размеру и росту данных, сроку хранения и нагрузке на диск.

## 4. Helm-чарт

- **БД и кеш:** StatefulSet или ресурсы оператора, сервисы и отдельные PVC для каждой реплики там, где нужна персистентность. Требуются репликация и автоматическое переключение на уровне выбранной БД и кеша: три Pod сами по себе отказоустойчивости не дают. Размещаю реплики каждого компонента на разных worker-нодах через anti-affinity по hostname. Хранилище должно переживать отказ ноды или позволять восстановить реплику на другой ноде из оставшихся копий.
- **Фронтенд и бекенд:** отдельные Deployment и ClusterIP Service. Фронтенд принимает внешний трафик через Ingress, бекенд доступен внутри кластера. Использую readiness probes и распределяю реплики по узлам.
- **Окружения:** отдельные файлы values для dev/stage/prod. В них задаю образы и теги, replicas, requests, класс хранилища и настройки Ingress. Конфигурация без секретов хранится в ConfigMap, секреты передаются отдельно от Git.

Для БД и кеша предусматриваю PDB с сохранением как минимум двух доступных реплик, если выбранная схема рассчитана на работу двух из трёх. PDB ограничивает добровольные остановки, например при обслуживании ноды. Реальную работу при внезапном отказе проверяю отдельно: доступность сервиса, восстановление реплик и размещение в пределах оставшихся ресурсов.
